BatCave 0.2.1-rc.1 previews improvements to Windows collection, app grouping, and the live interface since 0.2.0.

- Windows connects automatically to the authenticated installed collector service. Ordinary desktop launches do not request administrator approval or require a collection opt-in. Installation, upgrade, and uninstall can still require approval. If the service is missing, stopped, incompatible, or unavailable, standard-access monitoring continues and the limitation stays visible.
- The Windows installer creates one shared **BatCave** Start entry for all users and records its ownership in a protected receipt. Repair and uninstall act only on the recorded entry; foreign or modified objects are preserved and reported. App startup no longer creates per-user Start links. Historical links and user-created copies remain outside that ownership record.
- Verified Windows desktop components and the authenticated collector can appear as one inspectable BatCave workload. Overview and the inspector use the same group identity and aggregate metrics, with individual components and measurement coverage available for inspection. Components whose ownership cannot be established remain separate.
- The live interface keeps its header and inspector controls usable at narrow widths and increased zoom. Machine-wide physical disk activity remains distinct from process read/write I/O, and group summaries do not invent a representative process narrative.
- Quiet Windows process-network intervals no longer claim that the ETW consumer has stalled solely because no recent callback arrived. Previously decoded values become held when freshness expires; before the first supported event, attribution remains pending. Actual errors and event loss remain visible, and unavailable rates are not shown as zero.
- Manual updates release their previous selection before checking again. A completed installation shows **Restart required** and asks you to close and reopen BatCave; it does not silently relaunch or keep offering another installation in the old process. Monitoring remains available after an offline or failed check.

This is a prerelease and is not offered by the stable in-app update feed. Windows packages use the existing unsigned publisher policy; Tauri updater signatures are required separately. macOS notarization remains pending the actual release workflow and package verification, and is not established by these notes.

Current source checks and retained native observations do not complete qualification for this new version. Public A-to-B updating with this client, failure and recovery cases, oldest-supported hosts, the complete Windows Start/install lifecycle, and supported Linux and macOS native update paths remain open. macOS kernel CPU is unavailable, and QUIC attribution has not been separately verified.
